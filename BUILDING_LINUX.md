# Сборка под Linux (нативно, без Wine)

Это маршрут A из [BUILDING.md](BUILDING.md) (`cpp → cc1 → maspsx → GNU as/ld → Python`) целиком на родных
инструментах Linux. Не нужны ни Wine, ни компиляторы SN Systems (`CC1PSX.EXE` / `CC1PLPSX.EXE`), ни PsyQ SDK, ни
образ диска. Компоновка естественная: объекты идут друг за другом в порядке компоновки, и адреса получаются сами из
этого порядка и размеров объектов.

Состояние (чистая сборка, Debian 13, 2026-10-13):

| Что | Результат |
|---|---|
| все единицы трансляции | компилируются; `ninja` с нуля — около 22 с на 2 ядрах (только то, что входит в диск), правка одного файла — меньше секунды до готовых `NFS4.EXE`/`FRONT.BIN` |
| размеры функций | **3522 / 3522** совпадают с ретейлом (`tools/linux/fn_sizes.py --all`) |
| компоновка | естественная (`linkers/link_order.txt`), без адресных файлов; неразрешённые символы и дубликаты — ошибка |
| `NFS4.EXE` | **байт в байт как на диске** (sha1 `c5c60d450bac…`) |
| `FRONT.BIN` | **байт в байт как на диске** (sha1 `d6c5b5d16e55…`) |

Совпадение байт в байт — это свойство исходников и набора компиляторов ниже, а не условие сборки. Если изменить
исходник, сборка останется рабочей: всё, что лежит за изменённым местом, просто сдвинется.

## 1. Установка тулчейна

```sh
tools/linux/setup_toolchain.sh          # --apt: заодно поставить пакеты хоста через apt; --all: ещё и необязательные версии gcc
```

Скрипт скачивает готовые сборки старого GCC для Linux x86-64 из
[decompals/old-gcc](https://github.com/decompals/old-gcc) (релиз 0.17) в `toolchain/linux/` (каталог в
`.gitignore`) и проверяет инструменты хоста.

**Нужны все пять версий.** Если одной не хватает, `build.py` подставит другую версию и выведет в stderr только
предупреждение `WARNING`. Сборка при этом пройдёт, но байт в байт уже не совпадёт.

| gcc из old-gcc | Заменяет (Windows, SN / PsyQ) | Для чего |
|---|---|---|
| `gcc-2.8.0-psx` | CC1PSX / CC1PLPSX из PsyQ 4.3 | основной поток (почти все единицы трансляции) |
| `gcc-2.7.2-psx` | CC1PSX из PsyQ 4.0 | единицы с `cc1_ver: 2.7.2` и ступень лестницы 2.7.2 (библиотеки Sony) |
| `gcc-2.8.1-psx` | CC1PSX / CC1PLPSX «2.8.1-sn» из PsyQ 4.4 | единицы с `cc1plus_ver: 2.8.1-sn` (replay, …) и ступень 2.8.1 |
| `gcc-2.7.2-cdk` | ступень `2.7.2-970404` | Cygnus CDK: FSF 2.7.2 не принимает её ограничения `"+m"` в asm |
| `gcc-2.6.3-psx` | ступень `2.6.3` | вставка функции в `syslib/psx/libetc/INTR.c` |

Версии 2.6.0, 2.91.66 и 2.95.2 (`--all`) для сборки не нужны.

| Пакет хоста (Debian/Ubuntu) | Зачем |
|---|---|
| `python3` (3.8+) | все скрипты сборки |
| `ninja-build` | система сборки (без неё работает последовательный путь, см. раздел 2) |
| `binutils-mipsel-linux-gnu` | `as`, `ld`, `objcopy`, `objdump`, `nm` (подходят любые binutils `mipsel-*`, см. ниже) |
| `cpp` | препроцессор (всегда запускается с `-nostdinc -undef`, поэтому годится любая современная версия) |
| `curl` или `wget`, `tar` | только для скрипта установки |
| `gcc` (необязательно) | запасной вариант для `tools/retail_sym.py` на хостах не x86-64 (`tools/dumpsym/dumpsym` лежит в репозитории как статический бинарник) |

Инструменты находятся автоматически. Переопределить их можно переменными:

| Переменная | Смысл |
|---|---|
| `NFS4_LINUX_TOOLCHAIN` | каталог тулчейна (по умолчанию `toolchain/linux`) |
| `NFS4_LINUX_CC1_VER` | версия gcc основного потока (по умолчанию `2.8.0`) |
| `NFS4_MIPS_BIN`, `NFS4_MIPS_PREFIX` | каталог / префикс binutils (по умолчанию первый найденный из `mipsel-none-elf-`, `mipsel-linux-gnu-`, `mipsel-elf-`, `mipsel-unknown-elf-` в `$PATH` или в `toolchain/linux/binutils/bin`) |
| `NFS4_CC1`, `NFS4_CC1PL`, `NFS4_CPP`, `NFS4_AS`, `NFS4_LD`, `NFS4_OBJCOPY`, `NFS4_MASPSX`, … | переопределение отдельных инструментов, как на Windows |
| `NFS4_JTBL_TAIL`, `NFS4_JTBL_TAIL_C` | переопределение правила размещения таблиц переходов (см. ниже) |
| `NFS4_PSYQ_SDK` | распакованные библиотеки PsyQ 4.3 для `link_stripped_check.py` (необязательно; без них проверка пропускается) |
| `NFS4_MKPSXISO` | бинарник mkpsxiso (по умолчанию `tools/psxiso/mkpsxiso`, сборка для Linux из репозитория) |

`python3 tools/toolchain.py` показывает, что именно найдено.

## 2. Сборка

Сборка описана в [Ninja](https://ninja-build.org/) (`apt install ninja-build`): инкрементальная и параллельная.

```sh
python3 configure.py        # один раз: пишет build.ninja (дальше он перегенерируется сам)
ninja                       # компиляция + естественная компоновка + NFS4.EXE / FRONT.BIN
```

Готовые файлы: `build/full_link/disc/NFS4.EXE` и `build/full_link/disc/FRONT.BIN`. Последним шагом печатается sha1
обоих и `== retail`, если файл совпал с диском.

Повторный `ninja` пересобирает только то, что изменилось:

| Что изменили | Что пересобирается |
|---|---|
| один `.c` / `.cpp` | эта единица трансляции + компоновка (меньше секунды) |
| заголовок | единицы, которые его включают (зависимости от `cpp -MD`) |
| `.s`, подключённый через `INCLUDE_ASM` / `.include` (`asm/nonmatchings`, `asm/cert`, `include/macro.inc`) | единицы, которые его подключают (depfile пишет `tools/tu_step.py`) |
| запись единицы в `PER_TU_FLAGS` или её функции в таблицах `PER_FN_*` (`tools/build.py`) | только эта единица: её флаги записаны в команду в `build.ninja`, а Ninja пересобирает ребро при изменении команды |
| `linkers/link_order.txt` | только компоновка |
| `tools/tu_step.py`, `tools/toolchain.py`, maspsx, бинарники компиляторов или `as` | всё |
| добавлен или удалён исходник в `recon/` или `src/` | `build.ninja` перегенерируется сам |

Не отслеживается только логика компиляции внутри `tools/build.py` (код `run_s` / `run_o`, а не таблицы). После её
правки: `ninja -t clean && ninja`. Переменные `NFS4_*` читаются при записи `build.ninja`, поэтому после их смены нужно
снова запустить `python3 configure.py`.

Цели:

| Цель | Что делает |
|---|---|
| `ninja` = `ninja disc` | объекты, которые входят в диск (`recon/` + `asm/header.s`), компоновка, `NFS4.EXE` + `FRONT.BIN` |
| `ninja link` | до `build/full_link/full.elf` (+ `full.map`) |
| `ninja objects` | только объекты, которые входят в диск |
| `ninja split` | ещё и `src/*.c` (сгенерированные splat'ом единицы, которые в диск не входят) |
| `ninja expected` | `expected/**.o` — эталоны objdiff, как их собирает CI (без `-DSKIP_ASM`) |
| `ninja all` | `disc` + `split` |
| `ninja sizes` | размеры секций собранного ELF рядом с ретейловыми (`tools/full_link.py --report`) |

Полезное:

```sh
ninja -t commands build/recon/game/common/ai.cpp.o     # точные команды одной единицы: cpp, cc1/cc1plus со всеми её флагами, as
ninja -j1 -v                                           # последовательно и с полными командами
ninja -t cleandead                                     # удалить объекты исходников, которых больше нет
python3 configure.py --strict-link                     # секции, не учтённые в link_order.txt, — ошибка компоновки, а не предупреждение
python3 tools/linux/fn_sizes.py --all                  # размер каждой функции против asm/nonmatchings (ретейл), без образа диска
```

Как это устроено: на каждую единицу трансляции в `build.ninja` два ребра. Первое — `<obj>.i` (препроцессор).
Второе — `<obj>.o` вместе с `<obj>.s`: `tools/tu_step.py` запускает cc1/cc1plus её потока, проходы `build.py` над
`.s` (обработка таблиц переходов, вставки отдельных функций) и maspsx + GNU as. Все параметры единицы — поток
компилятора, флаги из `PER_TU_FLAGS`, версия cc1 — берутся из того же плана в `tools/build.py`, что и при
последовательной сборке. Объекты получаются побайтово такими же (проверено на всех 1982 объектах `build/` и
`expected/`).

### Без Ninja

Последовательная сборка на Python по-прежнему работает (около минуты) и даёт те же файлы:

```sh
python3 tools/build_iso.py --no-iso                   # сам выбирает ninja, если он есть; --no-ninja — принудительно скрипты
python3 tools/build.py --skip-asm                     # компиляция всех единиц трансляции        -> build/**.o
python3 tools/full_link.py                            # естественная компоновка                   -> build/full_link/full.elf
python3 tools/elf_to_exe.py --split --no-compare      # PS-X EXE и два файла диска                -> build/full_link/disc/{NFS4.EXE,FRONT.BIN}
```

`full_link.py` генерирует скрипт компоновщика `build/full_link/nfs4_natural.ld` из `linkers/link_order.txt`
(`tools/gen_natural_ld.py`) и печатает размеры секций рядом с ретейловыми. `--no-compare` нужен, только если нет
`rom/nfs4-f.exe`.

Как устроена естественная компоновка (формат `link_order.txt`, атрибуты `pad=16` / `align=N` / `tail=N`, как
добавить новый файл), описано в [BUILDING.md](BUILDING.md#the-link-order-linkerslink_ordertxt).

### Образ диска

`tools/build_iso.py` использует Linux-сборку `tools/psxiso/mkpsxiso` из репозитория. Как и на Windows, ему нужен ваш
собственный дамп диска игры, распакованный `dumpsxiso` в `build/cd/<имя>/` вместе с `build/cd/<имя>.xml`:

```sh
tools/psxiso/dumpsxiso -x "build/cd/Need For Speed 4 v9.0" -s "build/cd/Need For Speed 4 v9.0.xml" your_disc.bin      # образ дорожки, 2352 байта на сектор
python3 tools/build_iso.py                            # ninja (если есть) + образ build/cd/<имя>.bin/.cue
```

## 3. Чем Linux-тулчейн отличается от Windows и почему

Каждое изменение ниже нужно только потому, что заменяющие инструменты ведут себя иначе. На Windows ничего не
меняется: там `tools/toolchain.py` возвращает прежние пути и настройки.

1. **Аналог PsyQ 4.3 — это `gcc-2.8.0-psx`, а не 2.8.1.** С 2.8.1 двенадцать функций выходили на 4–16 байт длиннее.
   С 2.8.0 размер каждой функции совпадает с ретейлом. `cc1plus` версий 2.7.2, 2.95.2 и 2.6.3 эти C++-единицы не
   компилирует.
2. **`cc1plus -fno-exceptions -fno-rtti`.** В FSF g++ исключения и RTTI включены по умолчанию: он выдаёт `.eh_frame`,
   посадочные площадки и функции type-info `__tf*`. SN cc1plus ничего этого не делал, и в ретейле этого нет.
3. **`as --no-pad-sections`.** Если ОС цели MIPS не просто `elf`, gas добивает каждую секцию до её выравнивания
   (`mipsel-linux-gnu-as` так делает, а Windows-овский `mipsel-none-elf-as` нет) и помечает `.text/.data/.bss` как
   выровненные на 16. С этим флагом размер секции в объекте равен её настоящему размеру. Выравнивание кусков задаёт
   скрипт компоновщика (`SUBALIGN(4)`, во front `SUBALIGN(8)`), а добивку до 16 у модулей Sony — атрибут `pad=16`.
   Поэтому пометка «16» на раскладку не влияет.
4. **Размещение таблиц переходов** (`tc.native_cc1plus_postprocess`, после cc1plus и до maspsx). FSF g++ кладёт каждую
   таблицу switch в `.rdata` сразу за её функцией. В объектах NFS4.EXE SN писал таблицы после всего остального
   (ретейловый `aih_btccop.obj` `.rodata` = SimpleMem, 5 vtable, затем `jtbl_80054F64`). В FRONT.BIN SN сохранял
   порядок FSF. Поэтому локальные таблицы переносятся в конец файла во всех C++-единицах вне `recon/frontend/`. Это
   правило проверено на всех 26 C++-единицах с таблицами переходов. Любой единый порядок для всех ломает одну из двух
   групп. Из C-единиц это нужно только `nfile.c` (`tc.JTBL_TAIL_C`).
5. **Проверка хешей** бинарников компиляторов SN для заменителей пропускается. Отсутствующие ступени лестницы
   заменяются соответствующим `gcc-<ver>-psx` с предупреждением (см. раздел 1).
6. Мелкие исправления переносимости:
   - include с учётом регистра в `recon/game/common/aitune.cpp`;
   - `dumpsym` собран из исходников и лежит в репозитории как `tools/dumpsym/dumpsym` (статический x86-64);
   - Linux-версии `mkpsxiso` и `dumpsxiso` помечены в git как исполняемые;
   - `link_stripped_check.py` пропускает побайтовое сравнение с SDK, если SDK нет.

### Не портировано

Исследовательские и вспомогательные скрипты сопоставления с зашитыми путями `C:/…` (`atsyms.py`, `brcensus.py`,
`cc1try.py`, `dial.py`, …) в сборку не входят и по-прежнему рассчитаны на Windows. При необходимости их можно
перевести тем же способом, через `tools/toolchain.py` (`tc.mips("objdump")`, `tc.DEFAULT_CC1PL`, …).
